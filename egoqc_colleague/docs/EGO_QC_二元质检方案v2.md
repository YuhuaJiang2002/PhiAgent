# Ego 数据二元质检方案（v2 · 二元判定版）

> 需求修正：**只做二元判断 —— 有问题就删，没问题就留。不输出原因分类。**
> 数据：CUS000001 / 项目 7（北京数采厂Ego）
> 状态：**方案，未动手**

---

## 一、任务定义

```
输入：一条 ego episode（多模态：视频 + 深度 + IMU + 手部姿态）
输出：keep（保留） / delete（删除）
```

不需要原因标签，不需要三态细分 —— 这大幅简化了问题。

---

## 二、好消息：真值已经现成，量也够

人工审核结果就是天然的二元标签：`auditStatus = valid → keep`，`invalid → delete`。

| 项 | 数量 | 说明 |
|---|---|---|
| 项目 7 已审核 episode（去重后） | **8756** | 人工逐条看视频得出的结论 |
| ├─ `valid` → **keep** | **3538** | 43.2% |
| ├─ `invalid` → **delete** | **4657** | 56.8% |
| ├─ `uncertain` 待确认 | 9 | **排除**，不宜当训练标签 |
| └─ `pending` 未审核 | 552 | **排除** |
| **干净的二分类池** | **8195** | 可直接用于训练 + 评测 |

**类别比例 43:57，不平衡不严重**，不需要过采样，普通损失函数即可。

这意味着：**不用再费劲构建 150 条的小数据集，8195 条全量才是真正的资产。** `cus000001_mixed150` 现在的作用降级为"小回归集"。

## 三、唯一必须先定清的口径问题 ⚠️

规范是三态，二元化会丢一类信息：

| 规范判定 | 二元映射 | 说明 |
|---|---|---|
| 无效 | **delete** | 无歧义 |
| 有效（全程干净） | **keep** | 无歧义 |
| **有效但含 bad 片段** | **？** | 规范说"整条保留、只切掉 bad 片段"，二元只能二选一 |

实测我建的 150 条：50 条 valid 里 **48 条含需切除的 bad 片段**，bad 时长占全数据集 **24%**。

**所以你要明确：二元判定的对象是什么？**
- **(a) 只判"这条视频要不要"** → 直接照 `auditStatus` 训练即可，方案最简单，今天就能出标签
- **(b) 最终要"干净的可用片段"** → 需要"二元判定 + 段级切除"两步。好消息是切除逻辑其实很简单：规范 1.2 只涉及**开头**和**多任务切分**，用确定性规则就能做（开头 >2s 手未出现、开头 10s 无关片段、人脸片段），不需要复杂模型

**我的建议：先做 (a)，把 (b) 作为第二步增强。** 如果你要的是干净训练集，两步都做，但难度可控。

## 五、三条技术路线

### A. 确定性指标 + 阈值（纯 CPU）

用多模态信号直接算指标：IMU 陀螺高频能量（抖动）、帧差滑窗（静止>10s）、时间戳间隔（丢帧）、亮度/色温时序（光线）、拉普拉斯方差分区（中心模糊/四角阴影）、**`keep_frame`/`left_kept`/`right_kept` 与 mano 手部框（手部出画，本数据现成字段）**、人脸检测。

- ✅ 零 API 成本、可解释、快、阈值可从 8195 条标注反推
- ❌ **只能覆盖技术性删除理由**

### B. VLM 二元判断

抽 30 帧丢给视觉模型，直接问"这条数据可用吗"。

- ✅ 开发最快、语义覆盖最全（"未按要求完成任务""无意义动作"这类只能靠它）
- ❌ 有成本/延迟、不可解释，而且**大模型对"丢帧/抖动"这类技术指标反而不敏感**

### C. 特征 + 监督分类器（推荐终态）

A 的确定性特征 + B 的语义判断 → 融合成二元分类头，用 8195 条标注训练。

- ✅ 指标最好、推理成本可控
- ❌ 工程量大一些

### 为什么不能只做 A：看真实删除原因的构成

我在抽样 100 条 invalid 上统计的原因分布：

| 原因 | 条数 | 能否纯技术判定 |
|---|---|---|
| 其他（兜底，未知内涵） | 34 | ❓ |
| 未按要求完成任务 | 27 | ❌ 需语义 |
| 采集设备屏幕露出 | 15 | 🔶 需专用检测器 |
| 全程静止无动作 | 9 | ✅ |
| 发生意外干扰 | 7 | 🔶 |
| 包含多余动作 | 5 | ❌ 需语义 |
| 视频模糊不清 | 2 | ✅ |
| 手部露出少 | 1 | ✅ |

**纯技术可判的只有约 12%，而"其他"占了 34%。** 结论：**只做 A 的召回率会很低，必须引入语义层（B/C）。**

| 阶段 | 内容 | 成本 | 产出 |
|---|---|---|---|
| **0（今天）** | 从平台拉全量二元标签：8195 条 `keep/delete`，按 `dataset_id` 分组划分 train/val/test | 零 | `binary_labels.jsonl` + `split.json` |
| **1（1–2 天）** | 路线 A 确定性指标基线（CPU 抽帧 + IMU/时间戳/手部信号） | 零 | 一版预测 + 指标报告 |

| **3** | C：特征 + 语义融合，调到目标指标 | — | 可用的二元质检器 |

**先跑阶段 1 和 2 拿到两个数字，再决定融合权重** —— 这样不会一上来就押错技术路线。

## 七、评估设计

- **划分方式**：必须**按 `dataset_id` 分组划分**，不能按 episode 随机分 —— 同一数据集内的 episode 高度同源，随机分会导致指标虚高。
- **指标**：召回率（有问题的被抓出比例）、精确率（判删除里真有多少问题）、F1。
- **关键：定义两类错误的代价**
  - **误删（假阳性）**：浪费采集成本，损失好数据
  - **漏放（假阴性）**：脏数据进训练集，污染下游模型
  - 你说"有问题就删除"，听起来更怕漏放。**建议先定"召回 ≥90%"作为约束**，再看精确率能到多少；宁可多删几条交人工复核，也不让脏数据流下去。
- **人工复核闭环**：把低置信度的交给人工，这比全自动更现实，也顺带产出更多标注。

## 八、需要你拍板

1. **口径**：有效但含 bad 片段算 keep 还是 delete？（第三节，唯一必须定的）
2. **错误偏好**：宁可**误删** 还是宁可**漏放**？（决定阈值方向）
