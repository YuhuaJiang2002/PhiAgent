**任务描述的实际形态（很关键）**，例如：

```
采集任务：王乾坤数据线收纳
  左手按压放置在白色收纳架上的平板电脑屏幕,右手在白色桌面边缘持握白色耳机。

采集任务：李学臣医药箱整理
  打开医药箱,取出并检查每种物品的保质期,然后放入,再检查下一个,最后扣上盖子
```

⚠️ **注意第一条：任务本身就要求操作"平板电脑屏幕"。** 所以提示词**不能**简单问"画面里有没有平板"——必须把任务描述一起给模型，让它区分"任务需要的平板"和"不该出现的采集设备屏幕"。这是第一版提示词最容易踩的坑。

## 一、输入构造

### 1.1 视觉输入

| 项 | 设计 | 理由 |
|---|---|---|
| 帧数 | **16–24 帧**起步，均匀分布 | 坏片段 100%，均匀采样可覆盖 |
| 分辨率 | **768–1024px 宽** | 400px 宽下我无法确认屏幕，太低会漏检 |
| 相机 | `observation.images.left_rgb` 为主 | 第二路 right_rgb 可做辅助（双目色差类） |
| **底部裁剪** | **额外附 2–3 张"画面底部区域放大图"** | 实测屏幕疑似出现在画面底部边缘、尺寸很小 |

### 1.2 时序通道（**必需，否则有一整类问题判不了**）

**均匀取帧在物理上无法判断"抖动"和"长时间静止"** —— 这两类需要连续帧之间的变化信息。

方案：每条额外附 **3 段连续帧**（每段 8 帧、间隔 0.1s，取自开头/中间/结尾），或由确定性代码算出**帧差统计**（平均帧间差分、静止区间占比、周期性晃动能量）作为**文本事实**喂给模型。

> 建议：两者都做。连续帧给"抖动/无意义动作"，数值给"静止时长/丢帧"。

### 1.3 文本输入

```
【任务描述】<来自 meta/tasks.jsonl 里非 bad 的条目>
【采集任务名】<来自平台 collectionTaskName，如"积木收纳">
【视频信息】时长 152.6s，30fps，分辨率 1920x1080
【覆盖度声明】共采样 24 帧（均匀 16 帧 + 细节 8 帧），另有 3 段连续帧
```

**盲测原则**：不提供数据集名、目录名、人工审核标签、`bad` 文本。

## 二、提示词设计（核心）

### 2.1 系统提示（7 条铁律）

```
你是第一人称（Ego）采集数据的质检证据审核员。你的判断决定一条数据是保留还是删除。

【铁律】
1. 只报告画面中直接可见的事实。不得从文件名、目录名、任务名推断任何结论。
2. 任何"存在问题"的判定必须给出可直接核对的帧 ID；帧号合法不代表帧内容支持你的主张，
   你必须亲自核对画面语义。
3. "没有看到问题"不能作为"没问题"的证据。只有当你要求的帧数都满足、且画面确实清晰可判，
   才能判定"未出现"；否则必须选"无法判断"。
4. 判定"无法判断"不会被惩罚，编造证据会被追溯。证据不足时一律选"无法判断"。
5. 你只回答被问到的这几条问题，不做总体结论。总体结论由确定性代码生成。
6. 任务描述中提到的物品（如平板、手机）如果是任务本身要求操作的，属于正常，不得判为问题。
7. 只输出一个合法 JSON 对象，不要输出 Markdown。
```

### 2.2 问题 1：设备/屏幕/平板/手机/腰包 露出（覆盖 ≈50%，最高优先级）

```
【问题1】画面中是否出现了"不该出现的物品"？
需要检查的类别：
  (a) 发亮的屏幕：手机、平板、显示器、采集设备的显示屏
  (b) 手机或平板本体（无论屏幕是否点亮）
  (c) 采集员随身佩戴的包具：腰包、挎包、收纳袋
  (d) 采集设备本体：外壳、夹具、线缆接头、支架

【判定要点】
- 只统计属于采集员或采集设备本身的物品；桌面上的任务道具不算。
- 若任务描述里明确提出要操作平板/手机（例如"按压平板电脑屏幕"），该物品属于任务道具，不算问题。
- 画面边缘只露出一角也算出现。
- 出现在任意一帧即算出现；不需要全程出现。

【必须回答】
1. 四选一：未出现 / 疑似出现但看不清 / 明确出现 / 无法判断
2. 若选"疑似"或"明确出现"：给出至少 2 个帧 ID，并说明
   - 是什么物品（手机/平板/屏幕/腰包/设备本体）
   - 出现在画面的哪个位置（上/下/左/右/中央/边缘）
   - 大约占画面多大比例
3. 反证：有没有帧显示画面中完全没有这些物品？给出帧 ID。
4. 若你采样到的帧无法覆盖整个视频，必须说明并考虑选"无法判断"。
```

### 2.3 问题 2：任务是否按描述完成（覆盖 ≈26%）

```
【任务描述】{task_text}

【问题2】视频是否按任务描述完成了该任务？
【判定要点】
- 必须看到任务的关键动作确实发生，准备动作（伸手、对准、靠近）不算完成。
- 必须看到任务的终态符合描述。
- 若任务包含"放入/归位/放下"，必须看到物体确实被放置并停稳；只看到手持不算完成。
- 若任务描述里出现"尝试但未成功"这类字眼，则任务本身就是"尝试"，不要据此判失败。
- 不要因为视频结尾突然停止就判未完成，除非终态明显与描述不符。

【必须回答】
1. 四选一：完成 / 部分完成 / 未完成 / 无法判断
2. 若选"部分完成"或"未完成"：给出至少 3 个帧 ID，说明
   - 实际做了什么
   - 与任务描述差在哪一步
   - 缺少的关键动作或终态是什么
3. 反证：有没有帧支持"任务其实完成了"？给出帧 ID。
```

### 2.4 问题 3：画面模糊（覆盖 ≈16%）

```
【问题3】画面清晰度是否影响判断手部动作？
【分级标准】
- 清晰         ：手部轮廓、手指分界、所持物体边缘均可辨认
- 轻度模糊     ：整体可见，但细节吃力
- 严重模糊     ：手部区域糊成一片，无法判断手在做什么
- 中心区域模糊 ：画面中心区域明显比边缘模糊（可能两侧都糊）
- 画面发白/过曝：大面积高亮导致细节丢失

【必须回答】
1. 五选一：清晰 / 轻度模糊 / 严重模糊 / 中心区域模糊 / 画面发白
2. 若选后四项：给出至少 3 个帧 ID，说明模糊区域在画面的哪个部位、占多大面积
3. 说明该状况是全程还是只出现在某段时间
4. 反证：有没有帧显示画面清晰？给出帧 ID。
```

### 2.5 问题 4：时序类与无意义动作（覆盖 ≈5%）

```
【问题4】是否存在明显的画面抖动、长时间静止或无意义动作？
【判定要点】
- 抖动：画面内容有规律地左右/上下晃动（抖腿、头部大幅晃动）。请比较连续帧序列。
- 长时间静止：连续超过 10 秒画面几乎无变化（对照给出的帧差数值）。
- 无意义动作：摸鼻子、抓痒、玩手机、聊天、休息等与任务无关的动作持续超过 10 秒。
- 废弃/测试片段：明显的调试、试拍内容（通常很短且无任务动作）。

【必须回答】
1. 多选：都没有 / 有抖动 / 有长时间静止 / 有无意义动作 / 疑似测试片段
2. 若选中任一项：给出对应的连续帧序号或帧 ID，并估计持续时长
3. 反证：说明哪些时段是正常任务动作。
```

  "q1_foreign_object": {"verdict": "未出现|疑似|明确出现|无法判断",
                        "items": [{"type": "平板", "frame_ids": [], "position": "底部中央", "area_pct": 5}],
                        "counter_evidence": [{"frame_ids": [], "claim": ""}]},
  "q2_task_completion": {"verdict": "完成|部分完成|未完成|无法判断",

  "q3_blur": {"verdict": "清晰|轻度模糊|严重模糊|中心区域模糊|画面发白",
              "frame_ids": [], "region": "", "span": "全程|局部", "counter_evidence": []},
  "q4_temporal": {"flags": [], "frame_ids": [], "duration_s": null},
  "coverage": {"total_frames_seen": 24, "covers_whole_video": true, "gaps": []},
  "confidence": 0.0

### 2.7 聚合规则（**代码定结论，模型不参与**）

```python
def decide(r):
    if r.q1.verdict == "明确出现":                 return "delete", "foreign_object"
    if r.q2.verdict == "未完成":                   return "delete", "task_incomplete"
    if r.q3.verdict in ("严重模糊","画面发白"):     return "delete", "blur"
    if "有抖动" in r.q4.flags and r.q4.duration_s and r.q4.duration_s > 10:
                                                   return "delete", "shake"  # 阈值待定
    if "有长时间静止" in r.q4.flags:                return "delete", "static"
    if "疑似测试片段" in r.q4.flags:                return "delete", "test"
    # 证据不足 → 交人工，不猜
    if "无法判断" in (r.q1.verdict, r.q2.verdict, r.q3.verdict) or not r.coverage.covers_whole_video:
                                                   return "needs_human", "insufficient"
    if r.q3.verdict == "中心区域模糊":              return "needs_human", "center_blur"
    return "keep", ""
```

**阈值与规则全部是代码常量**，可按"宁可误删 vs 宁可漏放"整体平移。

## 三、调用架构与成本

| 方案 | 调用次数 | 说明 |
|---|---|---|
| **Stage 1：单次多问** | **1 次/条** | 4 组问题一次问完，输出一个 JSON。本地模型成本=算力，可接受 |
| **Stage 2：反证审计** | 0.2 次/条 | 只对 Stage 1 判 delete 或低置信的条目，再跑一次"请找证据推翻这个结论" |

**Stage 2 是防幻觉的关键**（借用 rve 的 Reverse Audit）：如果模型找不出反驳证据，才最终判 delete。

**Token 预算粗估**：24 帧 @ 768px ≈ 每帧 400–700 token → 约 1.2–1.7 万 token/条（含文本）。对本地 7B/32B 模型都是可承受的；对 72B 需要看显存。

## 四、评测方法（怎么知道提示词好不好）

### 4.1 测试集构建（分层抽样，约 350–400 条）

| 分层 | 条数 | 用途 |
|---|---|---|
| 采集设备屏幕露出 | 50 | 测第一问题召回 |
| 其他（含写明原因的，如"平板一直在画面中"） | 50 | 测第一问题召回（补充） |
| 未按要求完成任务 | 50 | 测第二问题召回 |
| 视频模糊不清 | 30 | 测第三问题召回 |
| 包含多余动作 / 全程静止 / 手部露出少 | 各 20 | 测小项 |
| **有效（valid）** | **100** | **测误报率 —— 必须有** |
| 合计 | **约 350** | |

**按 `dataset_id` 分组划分**（避免同数据集泄漏），划出 dev / test 两半：dev 用于迭代提示词，test 只在最后跑一次。

### 4.2 指标

| 指标 | 定义 | 为什么 |
|---|---|---|
| **按原因召回** | 某个原因类的无效条中，被判 delete 的比例 | 能看出模型对哪类问题失效 |
| 整体召回 | 全无效条中被判 delete 的比例 | 漏放率 |
| **整体精确率** | 判 delete 中真为无效的比例 | 误删率 |
| **误报率** | valid 条中被判 delete 的比例 | 好数据被删的代价 |
| F1 | 综合 | — |
| **证据有效率** | 抽样 30 条判 delete 的，人工核对它给的帧是否真支持 | **测幻觉，比准确率更重要** |

### 4.3 迭代循环

```
写 prompt v1 → 跑 dev 集 → 看混淆矩阵 + 按原因召回
   → 找出"判错的那一类" → 定位是问题措辞、帧数、分辨率还是模型能力
   → 改 prompt v2 → 再跑 → 直到达标
   → 最后跑 test 集一次，作为最终数字
```

**每轮必看的三样**：① 漏检的都是什么原因；② 误删的理由是什么（有没有幻觉）；③ "无法判断"的比例（太高说明帧数/分辨率不够）。

## 五、执行步骤

| Step | 内容 | 产出 | 预估 |
|---|---|---|---|
| **0** | **前置调查**：拿 10–20 条"采集设备屏幕露出"，高分辨率 + **每秒 1 帧密集取帧**，人工确认"屏幕到底长什么样、出现在哪、占多大" | 屏幕的视觉特征描述 + 典型样例图 | 半天 |

| 2 | 写 v1 提示词，跑 dev 集 | 基线指标 + 错例清单 | 1–2 天 |
